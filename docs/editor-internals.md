# Editor internals

How the SvelteKit app is wired, and the non-obvious rules that keep saves from silently corrupting.
Stack: SvelteKit 2 + **Svelte 5 runes**, Tailwind 4, **bun**, Tauri 2 (fs + dialog plugins). Runs as
both a website and a desktop app from one codebase (`adapter-static`, `ssr = false`).

## Commands

```bash
bun run dev         # vite dev server (port 5173, or $PORT — see vite.config.ts)
bun run check       # svelte-kit sync + svelte-check (the real gate; also checks .svelte files)
bun run lint        # eslint
bun run build       # adapter-static production build
bun run extract     # regenerate all game data from the installed game (docs/migration.md)
bun run check:data  # cross-check the generated JSONs without re-extracting
```

`bun run check` is the type gate — plain `tsc` misses everything inside `.svelte`. Always run the
Svelte MCP `svelte-autofixer` on any component you touch before finishing (repeat until clean); it's a
hard project rule.

`platform.ts` answers "which runtime is this" **once**, for both folders the editor opens. `runtime()`
returns `tauri` / `fs-access` / `download`, and `DirOps` is the read-write-exists-list-stat-grant
plumbing over a directory that `SaveDir` and `BackupFolder` are each a view of. Before it existed the
same three-way branch was written out in both modules, along with two copies of the File System
Access boilerplate and the same `showDirectoryPicker` type shim twice.

`SaveDir` abstracts *where* files come from, so the same code runs against a Tauri folder, a browser
folder handle, or an in-memory test dir. `pickSaveDir()` picks a backend by capability:

- **Tauri** — `@tauri-apps/plugin-fs`, in place.
- **Chromium** — File System Access API (`showDirectoryPicker`), in place.
- **Firefox/Safari** — neither can write a real folder, so `pickWebUpload()` returns a
  `DownloadSaveDir`: the user picks the folder via a directory `<input>`, every file is read into an
  in-memory `Map`, writes accumulate there, and `exportChanges()` hands back a zip of the changed
  files. `supportsInPlaceSave()` gates the UI; `isDownloadDir()` switches the Save
  button to "Download changes". The save codec, accessors, and `saveSlot` are unchanged — only the
  `SaveDir` differs. It keeps a second, untouched `Map` of the folder **as uploaded**, handed out by
  `asUploaded()`: a backup taken here must be the moment the game left, and the live store has been
  accumulating the session's edits since the first keystroke.

`loadSlot` eagerly loads `levelinfo`/`vault`/`rundata`;
`loadFile(slot, name)` lazily loads and caches the heavier optional files (`entities`, `graph`,
`mapicons`) into `slot.files`. `saveSlot(slot, names)` writes the named files and nothing else — it
takes no backups, because backups are a deliberate act with their own controls (below).

## Backups are whole-folder zip archives

**A save is one moment.** The game rewrites `world`, `map` and `fow` as a run continues, so a restore
point holding only the files the editor touched puts an old ship into a map that has moved on. That
is what sank the `*.bak` scheme editor ≤1.0.2 used: it copied file-by-file on the first write, the
copies were made at different moments as the feature grew, and the whole thing lived in the folder it
was protecting. Existing `*.bak` files are left strictly alone — they are someone's restore point —
but nothing writes new ones.

A backup is now `save001_2026-07-29_14-30.zip`: every file in the folder, under a `save001/` prefix
so extracting it by hand over `saves/` puts the folder back where it came from. `*.bak` and `*.zip`
are excluded — the first is an older moment and half the folder again in size, the second keeps an
archive out of the next archive.

**The backup folder is meant to sit outside the save folder, and is not stopped from sitting inside
it.** Those are two different statements and both hold: backups outliving the thing they protect is
the whole point, so nothing suggests the save folder — but it is the user's disk, and if they point
it there anyway the `*.zip` exclusion above is what keeps each archive out of its own successors.
The editor advises; it does not police.

- **`zip.ts`** is a classic ZIP reader and writer. `makeZip` deflates through `CompressionStream` and
  keeps whichever of stored/deflated came out smaller per entry (a 12 MB save folder packs to 7.6 MB;
  the LZF-compressed Odin files don't move, `world` and the PNGs do). `readZip` parses through the
  **central directory**, not the local headers, because that is the copy a stream writer is allowed
  to fill in afterwards. It is tolerant of archives this app didn't write — a zip made by the file
  manager is a real backup — and intolerant of ones it cannot honour: encrypted, zip64 or exotically
  compressed entries throw *by name* rather than being skipped, since a half-restored folder is worse
  than none. Every entry's CRC is verified.
- **`backup.ts`** is the archive layer: `packSaveFolder`, `archiveName` (collisions bump `-2`),
  `openArchive` and `unpackInto`. `openArchive` flattens paths to their file name (hand-made archives
  carry a folder prefix, the editor's carry the save's name) and then refuses three things: an
  archive holding **more than one folder** — a zip of the whole `saves/` directory flattens
  `save001/vault` and `save002/entities` to different names, so nothing else would catch it, and the
  result is one run's ship in another run's map; one **missing** `levelinfo`/`vault`/`rundata`; and
  one where those three are present but **do not decode** (`REQUIRED_FILES` + `decodesAsOdin` in
  `slot.ts` — the same gate `loadSlot` applies, because a file called `vault` proves nothing until it
  parses as one and `unpackInto` commits to whatever it is handed). `unpackInto` overwrites what the
  archive holds and **deletes nothing**: the save file set is fixed, so the only extras are old
  `*.bak` files.
- **`remember.ts`** is how a folder is found again next session, and two are: the save folder that was
  last opened and the folder archives are kept in, under separate keys so pointing backups somewhere
  else never moves the save. Tauri keeps an absolute path in `localStorage`; Chromium keeps the
  `FileSystemDirectoryHandle` in **IndexedDB** (the only store that can hold one) — `DirRef` is the
  union of those two, and `dirFrom()` reopens either. A way back is not a permission: on Chromium that
  still has to be asked for on a click (`DirOps.grant`), which is why `rememberedSaveDir()` probes
  `REQUIRED_FILES` and hands back nothing it could not already read.
- **`backup-folder.ts`** is where archives live: a folder picked once and remembered.
  Firefox/Safari get a `BackupFolder` that is the download folder — `restorable: false`, so
  the UI hides Restore, says why, and points at a runtime that can do it rather than naming the
  download folder as though it were a choice. `remove()` throws the same way `read()` does there.
  Deleting an archive is that one call and nothing else: it is **permanent** on both real backends —
  the fs plugin unlinks, `removeEntry` removes — so the asking is the UI's job, not the folder's.
- **`settings.svelte.ts`** is the reactive face of the two remembered settings (the folder, and
  whether opening a save offers a backup). It is a module singleton rather than fields on
  `EditorState` because the footer outlives the editor: `OptionsDialog` hangs off `AppFooter` and is
  reachable with no save open at all, which is what makes a question you switched off switchable back
  on. Two copies of that state would disagree the moment either side wrote one. The ask-on-load flag
  lives here rather than in `save/`, which knows nothing about dialogs.
- **`editor/backup.svelte.ts`** is `BackupState`, reached as `editor.backups`: the load-time question,
  the Backup action, the restore browser and the two confirms in front of it. Separate from
  `EditorState` because it changes for its own reasons, and it borrows only the open folder, the wait
  overlay and `reload()`. One error line for all of it — a folder that won't open and an archive that
  won't read are the same news to whoever clicked. `pending` (a restore, read and checked) and
  `doomed` (an archive marked for deletion) are never both set: each question replaces the list it was
  asked from, so `RestoreDialog` is three screens rather than a modal over a modal. The delete runs
  without the wait overlay — a backup is 12 MB through a compressor, this is an unlink — and it does
  **not** read the archive first, because a corrupt one is exactly the archive somebody wants gone.

Three rules the callers follow, all learned from the platform:

- **`settings.require()` runs first, straight off the click** — before any work and before the busy
  overlay. It picks a folder if there is none *and renews the grant on a remembered one*: a Chromium
  handle read back from IndexedDB has no permission until it is asked for, asking needs a live user
  gesture, and zipping 12 MB spends it. Ask afterwards and the prompt arrives behind a full-screen
  wait, or is refused outright once the gesture has expired — after all the work is done.
  `settings.recall()` is the other half: it reads the folder back *without* asking, for the screens
  that only need to name where a backup would go.
- **The list is read by whatever opens the restore dialog**, not by an `$effect` inside it, for the
  same reason: it is IO that may open a picker, so it has to ride the click.
- **A restore is all or nothing.** `unpackInto` reads every file it is about to overwrite before it
  writes the first, and puts them back if a write fails part way — otherwise a full disk at file 7 of
  10 leaves a folder that is six files from the archive beside four from the run, which is the exact
  two-moments-at-once this whole feature exists to prevent. When the rollback itself cannot write, the
  error names the files left holding the archive's copy; that case cannot be repaired from here and
  must not be swallowed.

**A restore can also start with no save open.** The title screen offers one when
`backups.lookForArchives()` — run on mount, silent, and deliberately `recall()` rather than
`require()` — could read the backup folder and found something in it. That button is `browse()`, the
same one the save strip has: it opens the list of archives over whichever screen is up and **loads
nothing**. Which is the whole point — a restore is for the save you can no longer use, so making one
open first would make the offer useless exactly when it is needed, and it put the browser on top of a
freshly decoded editor nobody asked for. `RestoreDialog` is therefore mounted in `+page.svelte`
outside the `slot` branch, alone among the dialogs, and reads no `editor.slot` anywhere. Where the
backup folder could not be read the offer is not made at all, which on Chromium is a remembered
handle whose grant lapsed with the last tab; Tauri's scope survives a restart, so on the desktop app
the offer tracks the folder exactly.

**Where it lands is settled when an archive is picked, and usually without asking.** An archive
carries the files and not the folder they belong in, so `prepare()` calls `#destination()` before it
reads anything, and stores the answer on `pending.dir` — which is what every line of the confirm then
names. The open save when there is one; otherwise `editor.lastSave`, which is the folder this session
opened or the one `rememberedSaveDir()` found on the way in. Neither costs a picker. Only a machine
that has never opened a save here has to ask, and it asks from `#destination()`, which runs on the
click that chose the archive — where the gesture a picker needs is still live. `recallLastSave()` is
the probe behind that: run once on mount so the click does not wait on the disk, awaited again in
case it was faster, and gated exactly like the offer — no picker, no permission prompt,
`REQUIRED_FILES` checked before the folder is reopened, so one the game has since deleted costs the
shortcut instead of throwing an error nobody asked for. On Chromium both probes lapse together with
the tab, so the shortcut is a within-session one and the picker comes back on a fresh tab; on Tauri
the persisted scope means it holds across restarts.

`confirm()` unpacks into `pending.dir` and then reloads it, which does double duty: where that folder
was open, everything in memory is a version of files that no longer exist, and where it was not, the
editor coming up on the restored save is the only thing the person who clicked gets to see.
`reload()` is also where `lastSave` is recorded, so a folder reached by restoring into it is a folder
to come back to, exactly like one that was opened.

**Nothing announces a success.** `EditorState` and `BackupState` surface `error` and nothing else: a finished action
already shows its result — the Save button goes quiet, a new archive appears in the restore list, the
editor is holding the restored values, the browser's own bar named the download. A line of prose
repeating that is a second thing to read that says nothing the screen did not. What *is* said out
loud is said before the fact: the restore confirm reads its numbers **out of the archive** (file
count, the folder it was taken from) rather than off its name, which is the one part of an archive
nothing verifies.

The Tauri side needs one plugin for this: **`tauri-plugin-persisted-scope`**. Picking a folder in the
dialog is what grants the app access to it — `capabilities/default.json` statically allows only the
game's own save directory — and that grant lives in memory, so without the plugin a backup folder
chosen once would be unreadable the next time the app started.

Scope is only half of it: **every `fs` command also needs its own `fs:allow-*` in that file**, and
`fs:default` grants none of the ones this app uses. A missing one fails at the call, not at build
time, and `folderOver.list` swallows a failing `stat` by design (a file that will not stat is still a
file that can be restored) — which is how the desktop build spent a while listing every archive as
`0 B · date unknown`. `platform.ts` currently needs `read-file`, `write-file`, `read-dir`, `exists`,
`stat` and `remove`; adding a call there means adding a line there.

## The load-bearing Svelte 5 rule: no deep `$state` on save trees

**A deep `$state` proxy stores mutations in its own signal storage and never writes them back to the
underlying object.** The serializer reads the raw objects, so if the UI edited through a proxy, saves
silently wrote the *pristine* tree (creating `.bak`s but byte-identical files). Worse, aliased paths
(`slot.rundata` vs `slot.files.rundata`, same raw object) get *independent* proxies. This was the
"edits don't persist" bug (commit 04e672d). Rules that follow from it:

- Save trees live in **`$state.raw`** (`EditorState.slot` in `$lib/editor/state.svelte.ts`). Never
  wrap the Odin trees in deep `$state` — also avoids allocating a signal per property of the ~7 MB
  `entities` tree.
- **All inputs write straight into the raw tree** through `$lib/editor/inputs.ts` (`numInput`,
  `ingredientInput`, `setShipResource`), never `bind:value` into a proxied path. The handler mutates
  the exact object the writer serializes — and it owns the whole editing rule for its field: the
  empty/NaN guard, the clamp (run resources ≥ 0, ship tanks `[0, max]`, counts rounded), and marking
  exactly the file the edit belongs to dirty. Panels pass bounds as options instead of implementing
  them.
- UI refresh is driven explicitly: `EditorState.version`, bumped by `editor.refresh()`, and reactive
  `SvelteSet`s (`dirtyFiles`, `loadedFiles`). Every panel's derived view reads `editor.version` so
  edits invalidate them. Click-driven mutations (add/remove/reorder/toggle) call
  `editor.touch(file)`, which marks the file and repaints in one step. For typed inputs the version
  bumps on `change`/blur, not every `input` (the delegation wrapper in `+page.svelte`), so
  in-progress decimal typing isn't clobbered.
- Because a derived recompute keeps the same underlying object identity, snapshot the scalars you want
  the keyed `{#each}` to react to into fresh row objects (see the `rows` derived in
  `ShipResourcesPanel.svelte`) rather than reading `pair.$v` directly in the template.

`RawTree.svelte` keeps a local `$state.raw` mirror of one node's value for display and writes through
to `container[key]` on edit — `container`/`key` are captured once (props never change for a keyed
node; the `state_referenced_locally` autofixer warning is intentionally silenced there).

## Accessor conventions (tree.ts / vault.ts / ship.ts / game/data.ts)

- `List<T>` → `listItems(node)` returns the backing `$0` array; `pushScalar` appends while maintaining
  `$types` metadata so it re-serializes.
- `Dictionary<K,V>` → **`dictPairs(node)`** returns the `{$k,$v}` array. Do **not** hard-code `$0`/`$1`;
  the pairs array's anonymous index shifts depending on whether the `comparer` was emitted inline or as
  a `$ref` (see save-format.md).
- Ship resources (`$lib/save/ship.ts`): `shipResources(entities)` (current `{$k,$v}` pairs, mutate
  in place), `shipResourceCaps(entities)` (`Map<resourceId, max>`) and `shipResourceRegen(entities)`
  (`Map<resourceId, perSecond>`). The last two are one grid walk (`sumGridEffects`) over two
  different `FloatSeries` effects — see game-code.md.
- Resource display names: `resourceLabel(id)` / `displayName(id)` in `$lib/game/data.ts`. `Resource`
  assets carry no `displayName`, so three of them would read as a colour codename; `RESOURCE_LABELS`
  maps `Resource Money`/`White`/`Purple` to **Money / Stamina / Gel**. The **ids are save-file
  keys** — only the label changes.
- `equippableModules()` mirrors the game's `ModuleData.Equippable`: a displayName **and** an icon.
  Named modules without an icon are embedded enemy parts and never appear in the picker. `isOwnable`
  then drops the three that pass that check but still cannot be owned: the `Embedded` category (SHIP,
  Crawler — they belong to an entity, not a vault) and any module with no effects, no weapon and no
  effect field, which is RED EYE alone, an unfinished asset that would do nothing in a grid slot.
- Ingredients: `DISABLED_INGREDIENTS` in `ResourcesPanel.svelte` hides the four the current build
  never hands out — Bond, Ex, Face and Strange Ball. They stay in `asset-names.json` (extraction
  reports what the game data holds, not what the game uses), so a build that starts granting one
  brings it back by deleting a string. Everything else is listed whether owned or not, since raising
  a count from zero is how you get one.
- Consumables: the vault holds a **fixed run of 8 slots**, empty ones carrying a `null` id (the game's
  `Vault()` seeds 8 and `RestoreFromMemento` rebuilds one slot per memento entry). `setConsumable`
  mirrors `Vault.Add` — it fills the first empty slot rather than growing the list, and returns
  **false** when there is none, since appending a ninth would write a vault the game never would.
  `reorderConsumables` reorders the filled slots and keeps the empties trailing, so the slot count is
  preserved. The UI hides the empty slots and offers an add button per absent consumable type instead.
  **Zero is not a state a slot may sit in**: the wheel draws only slots holding something while "is
  this already held" reads the id, so a slot left at 0 would vanish from the wheel *and* keep its
  consumable out of the add row — stranded with no way back. `setConsumableAmount` is the one rule
  for that (0 empties the slot); both the +/- stepper and the count field go through it, the field on
  `change` rather than `input` so typing "0" on the way to "10" doesn't empty the slot mid-keystroke.
- Modules: `addModule(vault, id, fields?)` appends a `Module+Memento` mirroring `Module.CreateMemento` — all
  four connections on, `powerLevel` at the asset's max, and **both** effect fields rebuilt from
  `module-info.json`: the `powerCore` (without it a placed module would provide no core) and the
  `levelModificationField` (without it an added BOOSTER CORE would boost nothing). New **reference**
  nodes must claim an unused `$id`: Odin resolves internal references (`$ref`) through those ids, so
  reusing one would silently repoint an existing reference. `maxOdinId(tree) + 1` supplies fresh ones
  (the memento plus two nodes per field). `savedEffectField(node)` reads a stored field back — the
  module's *rolled* shape, which is what the vault list draws and what the grid walk in `ship.ts`
  uses. `fields` overrides either shape, which is how the picker applies a choice made before Add.
  `moduleInfo(id)` exposes the module's colour/resource.
- `setSavedEffectField(vault, module, key, field)` changes the shape a module already in the vault
  projects. It rewrites the existing `ModuleEffectField` node **in place** rather than swapping it —
  the node's `$id` is what any `$ref` resolves through, so replacing it would strand those references.

## Generated data (regenerate on game update)

**`bun run extract`** regenerates all six JSON files under `src/lib/game/` from the installed game
in one command and then cross-checks them (`bun run check:data`). Full runbook, including what every
warning means: **docs/migration.md**.

The Python side is built on `scripts/punklib.py`: one shared UnityPy scan of the whole `Punk_Data`
folder, the Unity version auto-detected from the game files, and assets classified **by their C#
class name** (read via the raw-header `m_Script` pointer — the generated typetree misparses that
PPtr) instead of per-script field heuristics. Unknown classes and unknown effect types warn loudly
instead of being silently mis-filed.

- `asset-names.json` — id → `{category, assetName, displayName, …}`. Categories are class-derived
  (`Module`, `Weapon`, `Consumable`, `Ingredient`, `Resource`, `SlotType`).
- `module-effects.json` — module GUID → **every** decoded `ModuleEffect` plus slot level deltas. The
  eight C# effect subclasses all reduce to one shape (a `FloatSeries` magnitude, usually a resource,
  a few scalars), so `EFFECT_KINDS` in `extract-module-effects.ts` maps each type onto it. The
  intermediate `scripts/module-effects-raw.json` is gitignored.
- `resource-icons.json` — resource id → `{ color, orderInHud, icon, bar, barCompact, barMicro }`.
  A resource carries art at **four sizes**, all rendered by the one `ResourceIcon.svelte` (a
  `variant` prop, pixelated): the small HUD `icon` the editor shows by default, the full-size `bar`
  unit (the only large art that differs per resource; Money has none), and the compact/micro bar
  units, which are *shared* sprites the game tints with the resource's `color` — so the component
  masks and tints those two. Extracted game art *is* committed — see the note in game-code.md.
- `item-icons.json` — ingredient/consumable/module id → data-URI PNG of its item art, at **native
  size** and, for modules, **already tinted**. Module sprites on disk are white/grey stencils with
  black outlines; `ModuleIconWidget.SetColor` multiplies them by the module's `ColorAsset` at
  runtime, so the tint is baked in at extraction (`extract-item-icons.py`). Doing it there rather
  than with a CSS mask/blend keeps the editor rendering plain `<img>`s — a filter over the *scaled*
  bitmap would soften exactly the pixel edges the integer-scaling rule protects. A module with a
  white ColorAsset is left alone (that is its real colour), as is `Crawler`, whose sprite is
  authored pre-coloured and has no ColorAsset.
- `module-info.json` — module id → `{ color, resource, type, description, powerLevel: [min,max],
  powerCores, levelFields, weapon }`. Drives module tinting in the UI and supplies the defaults
  `addModule` needs — see the module-colour section in game-code.md. The two field lists are the
  *candidate* shapes (`SpriteDistribution.Draw` picks one per module built: five for POWER CORE,
  three for BOOSTER CORE, exactly one for everything else), drawn by `EffectFieldGrid.svelte`.
- `ui-sounds.json` — editor event → `{ sfx, volume, clips: [{ uri, weight }] }`, the game's own
  interface sounds as trimmed MP3 data URIs. Keyed by the game's sfx *name*, and the clip list keeps
  the game's weighted distribution so a future sound with variants needs no code change. See "The
  interface sounds" below. This is the one extractor that needs `ffmpeg`; without it the step is
  skipped with a warning rather than failing the run.

All need the Python venv with UnityPy. The scripts expect it at `/.venv` (gitignored):
`python -m venv .venv && .venv/Scripts/pip install UnityPy TypeTreeGeneratorAPI Pillow`. Don't keep it
in the scratchpad — the OS temp cleaner deletes package files out from under it.

## The pixel-art rule: integer scaling only

**Every ripped sprite is displayed at an exact integer multiple of its natural size, never in a fixed
CSS box.** The art is hand-drawn pixel art — most item icons are 24x24, the HUD glyphs 8-13 px. At a
fractional scale a source pixel covers a non-integer number of screen pixels, so edges shimmer and
single-pixel details drop out; a square `h-8 w-8` box also squashes the non-square glyphs (they are
mostly 13x12, 8x12).

`$lib/game/pixel-icon.ts` implements it: `pngSize()` reads the natural dimensions straight out of the
PNG's IHDR chunk (big-endian u32s at byte offsets 16 and 20, so the first 24 bytes suffice — no image
load, no layout pass), and `iconStyle(uri, scale)` emits `width`/`height` in px plus
`image-rendering: pixelated`. `ItemIcon`/`ResourceIcon` take a `scale` prop defaulting to **2x**.

The consequence upstream: **the extraction scripts must emit sprites at native size.** The old
`ITEM_MAX = 64` long-edge cap in `extract-item-icons.py` resampled by a fractional factor and broke
the grid before the browser ever saw it; it was removed.

## Game rich text: parse it, don't strip it

Module descriptions are authored as TextMesh Pro markup — `slowly regenerates
<color=#B32AAC>GEL</color>` — and the colours carry meaning: they are the resource colours, so the
tag is how the player sees which resource a module touches. Printing the raw string leaks markup;
stripping it loses the signal.

`$lib/game/rich-text.ts` parses it into a flat run list (a stack of active styles, since every tag
TMP allows here is inline styling) and `components/RichText.svelte` renders it. It is built as a
**tag table**, not a pile of regex replacements, because the game is in development and updates will
add tags:

- Supporting a new tag = one entry in `TAGS`.
- An **unknown tag is consumed, not printed** — the same thing TMP does — so new markup degrades to
  plain text rather than showing `<size=120%>` to the player.
- Only `<color>` appears in the current build; `b`/`i`/`u`/`s`/`br`/`space` are supported because
  they cost nothing and are the tags most likely to turn up next.

## Modules in the UI

Modules show in two deliberately different shapes: the vault tab draws each one as the game's own
tooltip card (`panels/ModulesPanel.svelte`), the add-module modal (`ModulePicker.svelte`) lists rows
via `components/ModuleList.svelte` with an `actions` snippet for its Add button. What the two share
is not their *layout* but everything else — grouping, ordering and the effect-field kinds live once
in `$lib/game/module-groups.ts` (with `moduleCard(id)` returning the info/colour/tier/stats both
surfaces open with), the pieces that are identical wherever a module is drawn are components
(`ModuleStatLine`, `ModuleGroupHeading`), and the shared copy styles (`punk-group-title`,
`punk-game-desc`, `punk-stat*`) are layout.css utilities.

- **Categories come from the game**, not a list in the editor: `ModuleData.moduleType` points at a
  `ModuleType` asset whose `displayName` is the shop category and whose `orderInShop` is the order.
  `moduleCategory(id)` reads it. Today that is WEAPONS, GADGETS, UPGRADES (the ship modules), WEAPON
  MODS, plus the single-module POWER / BOOSTERS / Embedded. A renamed or added category carries
  through on the next extraction with no code change.
- **The power-core field is hidden for modules that have no core** (`usesPowerCore(id)`, i.e. a
  non-empty `powerCores`). That is UPGRADES and WEAPON MODS, which also have a `powerLevel` range of
  `[1,1]` — the field could only ever read 1 there. POWER is hidden too, for the opposite reason: its
  `powerCores` shape is the area a core *supplies*, not an amount it draws, so a core count on a core
  counts nothing.
- **POWER and BOOSTERS are pinned to the top** of every grouped module list (`categoryRank`). Both
  categories act on their *neighbours* rather than on themselves, which makes them the modules whose
  placement matters most; the game's own shop order splits them (POWER first, BOOSTERS last).
- **Within a category, modules sort by resource then name** (`resourceRank`), in the order the player
  meets them: Stamina, Health, Gel, Caps, Electron, Tech, everything else last. Deliberately *not*
  `orderInHud` — that is the order the bars stack on screen (Caps first, Health last) and reads as
  arbitrary in a list. It also keeps each resource's modules adjacent and uniformly coloured.
- **Effect fields are drawn as diagrams**, the way the game does on a core's card
  (`ModuleEffectFieldWidget`): `EffectFieldGrid.svelte` renders the bool grid in the module's own
  colour. Every cell is drawn identically, the centre included — the game marks it no differently,
  and a ring around it only broke up the shape. It does three jobs — static diagram, one selectable
  option, or a paintable canvas — differing only in what wraps the cells.
- **The shape is selectable** wherever a list passes `onfieldchange` (`EffectFieldChooser.svelte`).
  The options are `effectFieldChoices`: every *distinct* orientation of every shape the asset can
  roll. That is not a liberty — `ModuleEffectField.Parse` rolls a mirror per axis and a quarter-turn
  when it builds a module, so all eight symmetries are fields the player could legitimately have got,
  and the shape stored in a save is rarely the sprite's base orientation. Symmetric patterns dedupe,
  which is why POWER CORE's five sprites offer 10 options and BOOSTER CORE's three offer 4.
  In the vault a pick writes the memento immediately; in the picker it is transient state keyed by
  module id, applied only when that row's Add is pressed, and dropped when the dialog closes.
- **Hand-painted fields** sit in the same row as the rolled ones but carry a user badge on the top
  edge (tooltip: "User-defined custom shape") and a square delete badge centred on the top-right
  corner, because the distinction that matters — the game could not have rolled this one — belongs on
  the shape rather than on a heading away from it. The warning that they leave the set of producible
  shapes lives in the painting modal. They work — see the hand-painted-shapes section of game-code.md for exactly why, and for the
  square, odd and lit-centre invariants `effectFieldProblem` (in `$lib/game/effect-field.ts`)
  enforces (non-square fields make the game's own
  `y * height + x` indexing read out of bounds and throw). A field that fails validation is never
  written: the painter's Add button is disabled and the store refuses it too. The user badge is the
  game's own health red, read from `resourceColor('Resource Health')` rather than hard-coded.
- **The centre cell is not paintable.** It is where the module itself sits, not part of the area it
  projects, so `EffectFieldGrid` renders it as a span rather than a button when painting (and
  `paintCell` guards it, and `effectFieldProblem` refuses a dark centre outright — the last matters
  because the validator is the only gate on the localStorage load path). A field with a dark centre
  would put the module outside its own effect, which no sprite the game ships can produce. It still
  *looks* like every other cell — only its handlers differ.
- **The canvas paints by dragging.** The cell you press down on decides the mode for the whole
  stroke: press a dark cell and the stroke draws, press a lit one and it erases. That is why `oncell`
  passes the value a cell should end up at rather than asking for a toggle — crossing a cell twice,
  or crossing one already in the target state, then changes nothing, whereas a toggle-per-cell would
  flicker the stroke against itself. `pointerdown`/`pointerenter` drive it (one code path for mouse,
  touch and pen) with `pointerup` on the window ending the stroke wherever it is released; the grid
  is `touch-none` so a finger paints instead of scrolling the dialog. A `click` still fires from
  Enter or Space on a focused cell, so that path toggles — it is recognised by `detail === 0`, which
  is what distinguishes a keyboard-synthesised click from a pointer one.
- **Painted shapes are a library, not a one-off** (`$lib/editor/custom-fields.svelte.ts`): a module-
  level `$state` array persisted to `localStorage` under `punk-save-editor:custom-fields`. The whole
  point of painting one is reuse, so it belongs to the person rather than to a save — every chooser
  in the app offers the same list, and deleting one removes it everywhere at once. Loading
  re-validates and silently drops anything malformed; this is a cache, not user data owed a
  migration, and a bad entry would otherwise walk straight into a save. Nothing here touches a save
  file — a custom shape reaches one only by being picked, along the same path as a rolled shape.
  Painting happens in its own modal (`CustomFieldDialog.svelte`) on a 14rem canvas; the dialog is
  mounted only while open, since a chooser exists per field per module row.
- **Every grid takes the same footprint** whatever its size: `EffectFieldGrid`'s `size` prop is the
  edge length of the *whole* grid (`1fr` tracks, not a fixed cell), so a 3×3 and a 7×7 both render
  56×56 and a row of shapes stays a row of equal tiles — the odd sizes read as coarser or finer
  rather than smaller or larger. The "add custom shape" button is a `size-14` dashed tile for the
  same reason, and slots in as the last item — square-cornered with a 2px dashed edge, matching the
  `ring-2` a selected shape carries, so it sits in the row as a tile rather than beside it. Grids are
  square-cornered: a rounded diagram would disagree with the square cells inside it. Both badge
  glyphs (the delete cross, the add plus) are drawn SVG rather than `×`/`+` characters — a glyph sits
  on the text baseline and carries the font's side bearings, so at these sizes it can be neither
  centred nor scaled against the box it fills.
- **Stat lines** (`$lib/game/module-stats.ts`) are the "+2 max Fuel" / "0.2 per shot" numbers. They
  come from two places: `WeaponData` for weapon modules (damage, fire rate, per-shot cost) and the
  decoded `ModuleEffect` list for everything else. Effects are evaluated at the module's *own* asset
  level — the unboosted figure — whereas the ship-resource totals evaluate them at their boosted
  grid level. A stat line with a `resource` renders that resource's HUD icon in place of its name,
  which is what the game does too (the written name stays as `sr-only` text).

## In-browser end-to-end testing

`open()` honors a dev-only hook: when `import.meta.env.DEV` and `window.__punkTestDir` is set, it loads
that in-memory `SaveDir` instead of prompting for a folder. This enables real end-to-end tests in the
dev-server page console (proxies only exist in the Svelte runtime, so a Node test can't catch the deep-
`$state` class of bug — it must run in the browser). Pattern:

1. Seed an in-memory `SaveDir` from fixtures (fetch `/test-save/<file>` after copying a real save into
   `static/test-save/`), record writes to `window.__punkTestWrites`, keep pristine copies in
   `window.__punkOrig`.
2. Drive the UI: native `HTMLInputElement` value setter + dispatched `input`/`change` events simulate
   typing. Svelte flushes async — a just-enabled button is still `disabled` in the same tick, so wait a
   tick before clicking.
3. Assert on written bytes: `import('/src/lib/save/lzf.ts')` and `/src/lib/save/odin.ts` are importable
   in the page; decode `window.__punkFiles[name]` and check values, and that bytes differ from the
   original.
4. Delete `static/test-save/` before committing.

Two traps if you drive that page from **headless Chrome** rather than the dev-server console:

- `--virtual-time-budget` fast-forwards `setTimeout`, so any wait for a genuinely asynchronous
  browser API (`decodeAudioData`, a fetch) is skipped and `--dump-dom` fires mid-run, printing a
  transcript that stops in the middle and looks like a hang. Attach over the DevTools protocol
  (`--remote-debugging-port`) and poll the page's own result element instead.
- A page under `static/` is served verbatim, so bare specifiers like `svelte` do not resolve in it.
  Keep the test body in a module under `src/` — Vite transforms that one — and let the HTML do
  nothing but import it.

The test hook also suppresses the load-time backup question — an automated run must not stop at a
modal, and the answer to that question is a native folder picker no script can drive.

There is **no automated suite** — not a Node one, not a runner in `package.json`. The browser walk
above is the whole of it, and it is driven by hand. The gap worth knowing about is `zip.ts`: it is
pure bytes and the obvious place for a `bun test` file, asserting that a packed folder re-reads byte
for byte, that a real archiver agrees the file is valid, and that archives made by hand still open.
Until that exists, treat any change to the ZIP reader or writer as unguarded.

## The interface sounds

The editor plays the game's own UI sounds. `src/lib/sound.svelte.ts` is the whole of the playback
side — `sound.play(name)` plus the on/off switch, which lives there rather than in
`editor/settings.svelte.ts` so that `Button`, the most-used component in the app, does not reach
through the backup layer to ask whether it may beep.

The clips come from the game's `AudioDatabase`, regenerated by `scripts/extract-ui-sounds.py` into
`src/lib/game/ui-sounds.json` (~25 kB of MP3 as data URIs). The key is the **sfx name** the game
files a sound under — `UI/OK`, `UI/Step` — not the clip file name, because a clip name says nothing
and an audio pass can repoint a name at a different file. Six are borrowed, all of them menu sounds:

| editor event | game sfx | plays when |
| --- | --- | --- |
| `click` | `UI/OK` | any `Button`, a `CloseBadge`, a tab |
| `hover` | `UI/Step` | a pointer lands on one, or focus arrives visibly, or the arrow keys step the tab strip |
| `open` / `close` | `UI/Grid/Open` / `Close` | a `Dialog` arrives and leaves — and `close` again under every edit: a tank unit, a wheel slot, a `+`/`-` step, a connection cell, a number field clicked, a consumable added or removed |
| `select` | `UI/Grid/ModuleSelected` | an effect-field shape is picked |
| `place` | `UI/Grid/ModulePlaced` | the picker's **Add** |

Five things about it are load-bearing, and each is a comment in the file too:

- **Web Audio and `atob`, never `<audio>` or `fetch`.** The desktop CSP allows `data:` for images
  only and sets no `media-src`, so both of the obvious routes are refused there. Bytes decoded by
  hand and handed to `decodeAudioData` are not subject to CSP at all.
- **`SoundName` is `keyof typeof uiSounds`.** A sound the game drops disappears from the generated
  JSON and `bun run check` then fails at every call site, rather than the app going quietly silent.
- **The caches are plain `Map`s.** `Dialog`'s `$effect` calls `play()`, which both reads and writes
  the retrigger clock — a `SvelteMap` there is an effect that assigns state it depends on, i.e. one
  that re-runs forever. This is the repo's one `eslint-disable`.
- **A sound before the page's first click is dropped, not queued**, or the whole backlog fires at
  once when the AudioContext is finally allowed to resume.
- **One `MASTER_GAIN`,** because the game's per-sfx volumes are levels inside a mix that the editor
  does not have. Its AudioMixer snapshot stores no float values and its groups carry no effects, so
  the number on the sfx is the whole story in game — and bare, the palette lands at −22 to −34 dBFS
  peak. The gain lifts all six together, so the game's relative balance is untouched.

The close sound rides the `<dialog>` element's `close` event rather than the effect that calls
`.close()`, because Esc closes the element itself and never reaches that branch. Note that the
in-app preview browser does not dispatch `close` on a `<dialog>` at all — verify that path in real
headless Chrome, per the traps above.

## Telling the user a new version is out

`$lib/update.ts` asks GitHub for the newest published release and the footer draws a link when it is
ahead of `appVersion` (package.json's version, substituted into the bundle by `define` in
`vite.config.ts`). That is the whole feature — **the app never updates itself.**

Tauri's own updater was the obvious alternative and was turned down: it installs over the app it is
running from, which neither the portable exe nor the deb/rpm bundles can honour, it needs a signing
key whose loss breaks updates for every copy already installed, and its `latest.json` is written by
each matrix job reading the file the previous one uploaded, which six parallel builds lose entries to.
None of that buys anything a link to the release page does not.

Details that are deliberate:

- **Only the desktop app asks.** A browser is already running whatever is deployed.
- **Failure is silent** — no network, a rate limit, and a repo with no releases all mean "say nothing".
- The answer is cached in `localStorage` for six hours, which keeps a reloading tab clear of the 60
  requests an hour GitHub allows without a token.
- A tag that is not `<n>.<n>.<n>` produces no notice rather than a wrong one, and `/releases/latest`
  never reports a draft or a prerelease.
- The desktop CSP has to allow `https://api.github.com` in `connect-src` (`src-tauri/tauri.conf.json`).
- The footer's other build-dependent link is the mirror of it: a browser is offered the desktop app,
  the desktop app is offered `punk-editor.henkys.dev`.

## Where the release notes are shown

`CHANGELOG.md` is parsed at build time (`$lib/changelog.ts`, Vite's `?raw` — there is no server to
fetch it from in the desktop app) and one release is drawn by `ReleaseNotes.svelte`. Two surfaces
wrap it:

- **The footer's overlay** (`ChangelogDialog`), which is what the Changelog link opens. It must not
  be a navigation: the open save lives in memory only, so leaving the editor for a page throws it
  away and coming back means picking the folder again. The link keeps its `href` so the URL can
  still be copied or opened in a tab — the handler steps aside for a modified click, and for the
  changelog page itself.
- **`/changelog`**, the same notes as a page, one `Section` card per release. It stays because
  CHANGELOG.md points the world at that URL.

## HTML5 drag and drop needs two things the defaults get wrong

The consumable wheel is the only place in the app that uses real HTML5 drag and drop — dragging a
slot around the ring reorders the vault. (`EffectFieldGrid`'s paint-across-cells is pointer events,
which none of this touches.) It shipped broken in 1.0.0 in two independent ways, both worth knowing
before adding a second draggable anywhere:

- **`"dragDropEnabled": false` on the window** (`src-tauri/tauri.conf.json`). Tauri defaults it to
  `true`, which installs an OS-level drop target on the webview that swallows HTML5 drop events on
  Windows — the config schema says so in as many words. The flag turns off Tauri's own file-drop
  event, which nothing here listens for. JSON has nowhere to write that down, hence this paragraph.
- **A `dragstart` must put something in the `dataTransfer`, and sprites must be `draggable="false"`.**
  A drag with no payload of its own is not inert: the browser looks inside the control for something
  draggable, finds the `<img>`, and makes *that* the drag source with the picture as the payload —
  so Windows offered the icon to the shell and the sprite was dragged out to the desktop instead of
  moving around the ring. Firefox is the other failure mode and refuses to start a payload-less drag
  at all. `ItemIcon` therefore marks its `<img>` undraggable, and `ConsumableWheel.dragStart` writes
  the consumable id as `text/plain`.

Chrome will show you which of these is happening: `Input.setInterceptDrags` over CDP reports the
payload the browser is about to hand the OS. Item art in the payload means the sprite won the
drag-source lookup.

## Dev server note

`vite.config.ts` uses `strictPort` on 5173 (Tauri's `devUrl`) but honors `$PORT` so a second dev
server can run beside another project's (e.g. the battery-monitor app also defaults to 5173).
`.claude/launch.json` has `autoPort: true`, so `preview_start` picks a free port automatically.
